Performance study · self-built .NET API gateway

The same system, built two ways.
Which wins? It depends on the load._

A URL shortener implemented twice — once as four microservices behind a from-scratch Kestrel API gateway (routing, round-robin load balancing, health-check failover), and once as a single layered monolith — sharing the same API, schema, and redirect cache. Benchmarked head-to-head with k6 on identical hardware. The result isn't a winner; it's a crossover.

The crossover

The gateway adds a fixed per-request cost; horizontal scaling pays it back only once a single process saturates. The two measured regimes sit on opposite sides of that line. (Schematic — the two points are measured; the curve between them is interpretation.)

One line: the gateway costs a fixed ~130 µs per request. Below saturation that makes the monolith faster; above it, three replicas more than repay the hop and the microservices win. The crossover is wherever a single process runs out of headroom.

The point of the exercise isn't to crown a winner — it's that "faster" is the wrong question. The right one is at what load, and this is the textbook microservices trade-off, measured on one real codebase instead of asserted.

System under test: URL shortener · hand-written Kestrel API gateway (no YARP) · auth / link ×3 / analytics services · Postgres · Dapper · Prometheus + Grafana · Next.js console · .NET 10.  ·  Monolith counterpart: the same features as one layered ASP.NET app.
